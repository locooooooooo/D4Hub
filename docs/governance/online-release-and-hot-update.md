## 1. 目标与边界

目标是在不突破 D4Hub 安全边界的前提下，形成可供 Owner 决策、后续工程实现和独立验收使用的 Windows 玩家分发、版本管理及重启式更新方案。这里的“热更新”只指应用发现新版本后下载、校验、由独立安装进程替换并重启应用；不采用进程内代码补丁，也不在 Diablo IV 运行期间注入或修改游戏。

本议题范围：

- 面向真实玩家的安装、卸载、升级、降级和修复体验。
- 应用版本、数据格式版本、更新协议版本及更新通道策略。
- 更新检查、下载、完整性验证、安装、重启、失败恢复和回滚。
- 更新清单、不可变产物、HTTPS、数字签名、代码签名证书和密钥保管。
- 构建供应链、最低系统版本、运行时打包选择和发布流水线。
- 隐私、遥测、崩溃上报的选择、知情同意、撤回和数据最小化边界。
- 离线、代理、DNS 失败、受限网络、限速和断点续传行为。
- 预览、灰度、稳定通道、事故响应、支持窗口和退出生命周期。

非目标：

- 本阶段不实现更新器、安装器、遥测或崩溃上报代码。
- 不采购证书、不创建云资源、不接入第三方服务、不上传产物。
- 不签名、不打标签、不创建 Release、不发布、不向玩家分发。
- 不改变现有功能、安全边界或唯一显式 D2Core 导入的网络边界。
- 不读取或写入游戏内存，不注入，不抓取游戏流量，不自动化输入或宏，不规避检测。
- 不把本地构建、夹具、模拟服务或源码测试当作签名、线上发布或玩家验收证据。

## 3. 玩家路径

### 3.1 首次安装

1. 玩家从 Owner 批准的官方入口获取安装器和可公开核对的版本、发布者及摘要。
2. Windows 显示可信发布者；安装器在安装前说明支持的系统、磁盘占用、更新方式和隐私默认值。
3. 安装不要求管理员权限，除非所选打包路径有明确且经批准的理由。
4. 首次启动保持遥测和崩溃上报关闭；更新服务与可选数据收集分开说明和同意。
5. 现有 `%LOCALAPPDATA%\D4Hub\build-state.json` 及公共构筑库不得被安装或升级流程无提示覆盖。

### 3.2 正常更新

1. 应用启动后或玩家手动触发检查；检查不得阻塞 HUD 正常启动。
2. 客户端只从当前通道的 HTTPS 清单读取版本信息，并验证清单真实性。
3. 客户端比较产品版本、最低兼容版本和数据迁移要求，显示版本、大小和发布说明。
4. 下载到隔离暂存区，支持取消、超时、重试和可选断点续传。
5. 安装前同时验证清单签名、产物 SHA-256、产物代码签名、发布者和时间戳。
6. 应用保存用户数据、关闭 HUD，由独立安装进程完成替换并重启。
7. 新版本健康检查通过后提交升级；失败则恢复已知良好版本，并保留可导出的本地诊断。

### 3.3 离线或受限网络

- DNS、TLS、代理、超时、403/404/429/5xx 或断网只显示“暂时无法检查/下载更新”，不得让应用启动失败。
- 使用指数退避和抖动，不在后台持续重试；玩家可关闭自动检查并保留手动检查。
- 未过期的已验证清单可以仅用于显示上次检查结果，不可据此安装未完整验证的产物。
- 支持从官方入口手动下载完整安装包；离线包执行同样的签名和完整性验证。
- 若未来存在最低安全版本阻断，阻断条件、宽限期和离线救援方式必须由 Owner 另行批准。

### 3.4 失败恢复、回滚和支持

- 下载中断：保留可验证分块或删除不可信暂存文件，不触碰当前安装。
- 校验失败：拒绝安装、删除或隔离产物、记录不含隐私数据的本地错误码。
- 安装失败：恢复旧目录、旧快捷方式和旧注册信息；用户数据采用先备份、后迁移、可逆或前向兼容策略。
- 启动健康检查失败：自动回到最后已知良好版本；不得在两个版本间无限循环。
- 已上线缺陷：冻结通道清单、停止推广、发布签名的已知良好版本或修复版本，并公开事故说明。
- 玩家可从“关于/诊断”查看版本、通道、最后检查结果和支持入口，并导出经过脱敏的本地诊断包。

## 4. 实现路径比较

下表只是决策输入，不代表路线已批准。

| 路径 | 优点 | 局限与风险 | 适合度 |
| --- | --- | --- | --- |
| MSIX + App Installer | Windows 原生包身份、安装/卸载和签名模型；可从 HTTPS App Installer 清单更新 | 证书信任、包身份和系统策略要求较强；自定义灰度、复杂回滚和便携分发受限；需要验证 HUD/全局快捷键行为 | 值得作为安全基线原型 |
| Velopack | 面向桌面应用的安装、通道、完整/差分包和重启更新体验较完整；可使用静态托管 | 引入第三方供应链和工具生命周期；签名、托管、回滚及企业网络行为仍需自行治理 | 值得作为产品体验原型 |
| ClickOnce | .NET/Visual Studio 生态内置，部署和按版本更新相对简单 | 通道、灰度、品牌安装体验、回滚控制和复杂发布编排能力有限 | 可作为低运维备选验证 |
| 自研引导器/更新器 | 协议、托管、灰度和恢复完全可控 | 安全、原子替换、UAC、锁文件、签名、代理、回滚和长期维护成本最高 | MVP 不推荐，除非前述路径存在已验证阻断 |

建议的决策方法是在隔离原型中同时验证 MSIX/App Installer 与 Velopack，使用同一组安装、升级、失败恢复、离线和 HUD 兼容测试，再由 Owner 基于证据选择。原型不得接入生产域名、证书或真实玩家通道。

## 5. 产品与技术要求

### 5.1 版本与兼容

- 提议使用 SemVer `MAJOR.MINOR.PATCH[-prerelease]` 表示产品版本；包平台需要四段数值版本时使用确定性、单调递增的映射。
- 稳定版本不可原地覆盖；清单和产物均以版本及摘要形成不可变地址。
- 应用版本、用户数据 schema 版本、更新清单 schema 版本分别管理。
- `MAJOR` 变化、数据不可逆迁移、最低系统版本提升和强制升级均属于受保护决策。
- 更新客户端只接受比当前版本更新且与当前通道、架构、系统和数据版本兼容的条目；降级只允许经过签名的恢复路径。

### 5.2 更新通道

- `stable` 面向普通玩家，`preview` 面向明确加入的测试玩家；是否增加 `internal` 由基础设施选择决定。
- 玩家从稳定通道加入预览必须明确操作；从预览退回稳定不得静默降级数据。
- 灰度优先采用显式测试群组和通道推广，不默认创建永久设备标识。
- 若需要随机灰度，分群算法、标识生命周期和隐私说明必须先获 Owner 批准。

### 5.3 更新清单和状态机

清单至少包含：schema 版本、产品、通道、目标版本、最低可升级版本、架构、下载 URL、字节数、SHA-256、产物签名要求、发布时间、发布说明 URL、是否必须更新、回滚目标、过期时间和清单签名。清单必须规范化后签名，客户端必须拒绝未知必填字段语义、过期清单、通道错配、版本倒退和签名无效。

客户端状态机：

`Idle -> Checking -> Available/UpToDate/CheckFailed -> Downloading -> Verifying -> ReadyToInstall -> Installing -> Restarting -> Healthy`

任何下载、验证、安装或健康检查失败都进入有界失败状态，并能回到当前可运行版本；不得通过跳过校验继续安装。

### 5.4 完整性与代码签名

- 所有清单、产物、发布说明和撤回信息只通过 HTTPS 提供；禁用明文回退。
- SHA-256 只能证明内容与清单一致；清单本身必须有独立数字签名或由所选平台的可信签名模型保护。
- Windows 可执行文件和安装器必须使用受信任的 Authenticode 代码签名并带可信时间戳。
- 客户端验证摘要、签名链、发布者、用途、时间戳和撤销状态；任一失败即拒绝安装。
- 代码签名证书类型、供应商、费用、公司/个人主体、SmartScreen 信誉预期和续期方案均待 Owner 决策。
- 私钥不得进入 Git、构建日志或长期普通 CI 变量。优先硬件、托管签名或不可导出密钥，并采用短期 CI 身份、最小权限和双人发布审批。
- 必须有密钥轮换、证书到期、泄露撤销、旧客户端信任迁移和紧急停发预案。

### 5.5 供应链

- 从干净、固定版本的 Windows 构建环境生成产物；锁定 SDK、工具和依赖版本。
- PR 验证与受保护发布工作流分离；普通 PR 和 fork 不得访问签名能力。
- 每个候选版本生成依赖清单/SBOM、许可证报告、源提交、构建日志、哈希和签名验证报告。
- 产物先上传到不可变版本路径，验证可下载性和签名后，最后更新通道清单。
- 发布身份使用最小权限；生产通道写权限、签名权限和托管管理权限分离。
- 第三方 action、打包器、时间戳服务、证书服务和 CDN 都进入供应链清单与应急替换计划。

### 5.6 系统与运行时

- 当前 README 声明 Windows 10/11，但 2026 年面向玩家发布前必须重新确认 Windows 10 生命周期、安全更新状态及实际玩家分布。
- 提议候选为 Windows 11 x64，以及仍处于 Owner 明确支持策略内的 Windows 10 x64 版本；最终最低版本待批准。
- `framework-dependent` 体积小但要求玩家安装正确 .NET Desktop Runtime；`self-contained` 安装更直接但体积和补丁成本更高。该选择需用真实安装和增量下载数据决定。
- 必须覆盖 100%、125%、150% DPI，标准用户、非管理员账户、常见代理/防火墙和无 .NET 环境。

### 5.7 隐私、遥测与崩溃上报

- 默认不发送使用遥测或崩溃报告；先提供完全本地、玩家主动导出的脱敏诊断。
- 更新请求即使不含业务标识，托管方仍可能看到 IP、时间、User-Agent 和 CDN 日志；隐私说明必须披露保留期、处理者和删除方式。
- 不默认创建永久设备 ID，不收集屏幕截图、游戏画面、技能栏、构筑内容、文件路径、窗口标题或玩家账号。
- 若未来引入遥测或自动崩溃上报，必须单独、明确、可撤回地 opt-in；更新能力不得与遥测同意捆绑。
- 事件 schema、采样、脱敏、保留、访问、跨境/第三方处理和删除流程需在写代码前获 Owner 批准。
- 玩家拒绝或撤回不降低核心 HUD、离线使用、手动更新或支持资格。

### 5.8 发布、灰度与事故响应

候选流水线：

1. Owner 批准版本范围和受保护决策。
2. 受保护分支/tag 触发干净构建、仓库测试、安全边界扫描和依赖/SBOM 检查。
3. 生成安装包和更新产物，签名后在全新 Windows 环境验证安装、升级、回滚和签名。
4. 上传不可变产物到非生产暂存位置，验证 HTTPS、缓存头、摘要和清单。
5. 经独立发布审批后发布 `preview`；观察明确同意的试用者结果。
6. 按预先批准的停止条件逐步推广到 `stable`；每次推广只改变签名通道清单。
7. 发现异常立即停止推广；按 runbook 冻结、回滚或发布修复，并保全证据。

事故最低动作：指定事件负责人、冻结发布、保存审计、评估证书/密钥、撤回不安全清单、恢复已知良好版本、通知受影响玩家、发布复盘和防复发任务。删除服务器文件不等于已安装客户端回滚；两者必须分别处理。

### 5.9 支持与退出生命周期

- 每个稳定版本声明支持窗口、最低受支持版本、兼容的数据 schema 和已知问题。
- 提议至少支持当前稳定版与上一稳定版的安全恢复，但具体期限和成本待 Owner 决策。
- EOL 需提前通知、保留最终签名完整安装包和离线导出能力、说明服务关闭后的应用行为。
- 停止更新服务后，现有本地 HUD 应继续运行；任何依赖在线服务的新增能力必须有明确降级路径。

## 6. 分阶段路线

### 阶段 0：治理与原型准入（当前）

- 形成独立 Goal、Task、QuestionSheet 和本规格。
- Owner 选择打包/更新路径、托管、签名、密钥、系统支持、隐私和发布政策。
- 在决策前只允许隔离、无生产凭据、无真实玩家的技术原型。

### MVP：可验证的本地发布候选（不等于线上发布）

- 生成可重复的版本化安装包和完整更新包。
- 在全新 Windows VM 验证安装、升级、保留用户数据、失败恢复、卸载和离线安装。
- 定义并测试签名清单格式、篡改拒绝和更新状态机；使用测试密钥只证明协议行为。
- 产出 threat model、SBOM、密钥操作 runbook、发布/回滚 runbook 和隐私文案草案。

### 阶段 2：签名暂存与受控试用

- 获批并配置真实代码签名与密钥保管；独立验证签名链、时间戳和撤销行为。
- 在非生产或受限预览通道验证真实 HTTPS、代理、CDN、限速和故障注入。
- 仅邀请明确同意的测试玩家，并将玩家验收与工程验证分开记录。

### 阶段 3：真实线上发布

- Owner 单独批准生产发布、版本、通道、推广比例、停止条件和支持承诺。
- 发布不可变签名产物和签名清单，执行灰度、监控、事故待命和玩家支持。
- 达到玩家验收门后再扩大稳定通道；未达标则停止或回滚。

### 后续阶段

- 评估差分包、带宽优化、多架构、企业代理支持和自动化事故控制。
- 只有在真实数据证明必要且隐私方案获批后，才评估匿名遥测或自动崩溃上报。

## 7. 可验证验收准则与证据分层

不同层的证据不可互相替代。

| Gate | 通过条件 | 合格证据 | 明确不算 |
| --- | --- | --- | --- |
| G0 治理提案 | 独立 Goal/Task 存在，受保护问题处于未回答/阻断状态，历史 Task 未变化 | SQLite 记录、事件序列、QuestionSheet、本文档摘要 | 投影文件单独存在、口头说明 |
| G1 本地打包测试 | 干净构建可重复；全新 VM 安装/升级/卸载/回滚；用户数据保留；离线可用 | 源提交、构建日志、产物哈希、VM 矩阵、失败注入报告 | `dotnet build`、源码单元测试、fixture 窗口 |
| G2 签名验证 | 真实受信代码签名、可信时间戳、清单签名、篡改/过期/错发布者拒绝、密钥审计通过 | `Get-AuthenticodeSignature`/平台验证报告、证书链、时间戳、负向用例、审计记录 | 测试证书、自签名、仅 SHA-256、CI 绿色 |
| G3 在线暂存 | 真实 HTTPS 暂存端点在受限网络、代理、断点、缓存和故障下符合状态机 | 端点与证书证据、网络矩阵、服务日志、回滚演练 | 本机 HTTP server、mock/CDN fixture |
| G4 真实线上发布 | Owner 批准指定版本；生产稳定/预览端点公开提供不可变签名产物；灰度与事故值守生效 | 接受的 Release/Decision、生产 URL、下载后摘要/签名复核、推广审计 | Git tag、上传成功回调、暂存环境 |
| G5 玩家验收 | 明确同意的真实玩家在支持的物理设备完成安装、更新、恢复和卸载，且达到预定成功率/严重故障阈值 | 去标识化测试记录、设备/系统矩阵、用户确认、问题闭环 | 开发者自测、VM、自动化 UI、进程存在 |

每个 Gate 必须记录失败条件：任何绕过校验安装、数据丢失、无法回滚、错误通道升级、未同意数据发送、签名发布者不符或安全边界回归均直接失败，不得豁免为通过。

## 8. 风险与待澄清项

受保护问题将进入 PKR QuestionSheet，未由 Owner 明确回答前保持阻断：

1. `distribution-stack`：MSIX/App Installer、Velopack、ClickOnce 或其他路径。
2. `release-hosting`：官方静态托管、GitHub Releases、对象存储/CDN，以及预算和地域。
3. `signing-certificate`：证书主体、类型、供应商、采购成本、续期和 SmartScreen 预期。
4. `key-custody`：硬件/托管签名、CI 身份、审批人数、轮换和应急撤销。
5. `runtime-packaging`：framework-dependent、self-contained 或双包策略。
6. `supported-windows`：最低 Windows 版本、x64 范围和支持期限。
7. `telemetry-crash-policy`：保持无自动上报、仅本地导出，或经同意接入指定服务。
8. `channels-rollout`：通道数量、灰度方法、停止阈值和是否使用设备分群。
9. `support-eol`：版本支持窗口、事故响应目标、最终包保留和服务退出承诺。
10. `production-release-authorization`：任何生产配置、签名、上传或真实玩家分发的单独授权。

主要工程风险：

- 更新器本身扩大网络与供应链攻击面，且一旦密钥泄露可影响全部玩家。
- HUD、全局快捷键、透明窗口和安装包身份可能在不同打包技术下表现不同。
- 不可逆用户数据迁移会阻断自动回滚。
- Windows 安全策略、代理、杀毒软件和 SmartScreen 信誉会造成首次安装失败或误报。
- 差分包、CDN 缓存和清单发布顺序错误可能导致混合版本或不可恢复升级。
- 更新端点的基础访问日志本身涉及隐私，即使应用不发送遥测。
- Windows 10 与 .NET 8 的生命周期会在发布周期内变化，需在每次发布门重新核对。

## 10. 状态口径

- 已提出：是。本规格、独立 PKR Goal/Task 和未回答 QuestionSheet 构成本议题提案。
- 已批准：否。用户授权整理治理产物，不等于批准路线、成本、第三方、证书、遥测、签名或生产发布。
- 已实现：否。没有实现安装器或更新器，也没有改变应用功能。
- 已测试：否。没有把现有仓库测试当作本议题测试；未来必须依次满足 G1-G3。
- 已验收：否。没有独立签名、线上或玩家验收记录。
- 已发布：否。没有签名、上传、Release、生产清单或玩家分发。
